## 2. 实现

### 2.1 stock-service：把空壳变成真实被调方

新增 `ProductController`：

- `GET /api/v1/products/{sku}` 查库存；
- `POST /api/v1/products/{sku}/deduct` 扣库存，库存不足返回 409，扣减用 `Map.compute` 保证并发下不会扣成负数；
- 两个接口都支持 `delayMs` 参数做**故障注入**，用于演示“调用变慢”与“调用超时”，不需要额外搭一套故障环境。

库存放内存（`APPLE` 100、`MILK` 50、`EGG` 30）。理由：评分表没有“商品表”分项，A5 的 12 分已被冰箱/菜谱的 11 张表覆盖，这里只需要一个真实可扣减的库存源。

### 2.2 order-service：下单 + 跨服务调用

- `StockClient`：`@FeignClient(name = "stock-service")`，地址来自注册中心，不写死 IP。
- `StockGateway`：库存调用的唯一出口，也是熔断落点。资源名 `stock-deduct`。
- `OrderService`：下单流程，资源名 `order-create`，流控落点。
- `OrderController`：把三种结果映射成三个状态码——201 创建成功、429 被流控、503 库存不可用或被熔断。

超时配置：

```yaml
spring.cloud.openfeign.client.config.default:
  connect-timeout: 1000
  read-timeout: 1500
```

### 2.3 Sentinel 规则

`SentinelRules` 在启动时用代码装载两条规则：

| 资源 | 类型 | 参数 |
| --- | --- | --- |
| `order-create` | 流控 QPS | count=2，快速失败 |
| `stock-deduct` | 熔断（慢调用比例） | 慢调用阈值 500ms、比例 0.5、最小请求 2、统计窗口 10s、熔断时长 10s |

规则写在代码而不是只留在控制台，理由：重启后不丢，演示可复现；答辩时能指着代码说明“限的是哪个资源、阈值多少、触发后走哪个方法”。阈值也通过 `smart-fridge.sentinel.*` 开放为环境变量，便于现场调参。

### 2.4 三种失败被显式区分

这是本轮最重要的设计点。如果只用一个 try/catch 吞掉所有异常，就无法回答“限流和熔断到底有什么区别”。

| 情况 | 处理位置 | 结果 | HTTP |
| --- | --- | --- | --- |
| 库存不足 | `StockGateway` 捕获 Feign 409，转 `BusinessException` | 原样上抛，不计入熔断计数 | 409 |
| 熔断打开 | `onBlocked` | 不再发起真实调用，直接返回原因 | 503 |
| 超时/连接失败 | `onFailure` | 剥到根因后给出“响应超时 / 无法连接” | 503 |
| 被流控 | `OrderService.onRateLimited` | 不进入业务逻辑，直接返回提示 | 429 |

`@SentinelResource(exceptionsToIgnore = BusinessException.class)` 保证“库存不足”这种正常业务结果不会污染熔断统计——否则用户多下几次超量订单就会把库存服务熔断掉，这是很典型的错误实现。

## 3. 发现的问题与修复

### 3.1 缺少 loadbalancer，order 服务起不来

第一次启动报：

```
java.lang.IllegalStateException: No Feign Client for loadBalancing defined.
Did you forget to include spring-cloud-starter-loadbalancer?
```

`@FeignClient(name = ...)` 走服务名发现，必须依赖 `spring-cloud-starter-loadbalancer`；fridge 服务之前用的是固定地址，所以没暴露这个问题。补依赖后正常。

### 3.2 application.yml 出现重复的 `spring.cloud` 键

手工追加 openfeign 超时配置时，在 `spring:` 下写了第二个 `cloud:`，YAML 会以最后一个为准，导致 Nacos 配置整段被覆盖。已重写整个文件，把 `nacos`、`openfeign`、`sentinel` 合并到同一个 `cloud` 下。

> 这类问题不会在编译期暴露，只会在运行期表现为“注册突然失效”，排查成本高。新增 YAML 段落时应整文件重写而不是字符串插入。

### 3.3 降级文案暴露实现细节

首次超时验证返回的是 `库存服务调用失败：RetryableException`——对使用方毫无意义。改为剥离到根因分类：

```
库存服务调用失败：响应超时（超过 1500ms 未返回）
```

对应 C3 要求的“失败有明确结果、调用端可正确识别处理”。

## 5. 汇报可用的话术

| 被问 | 回答要点 |
| --- | --- |
| 流控和熔断有什么区别 | 流控保护**自己**，按 QPS/并发数在入口拒绝多余流量；熔断保护**调用方**，看依赖的错误率或慢调用比例，超过阈值后一段时间内直接不调用，给下游恢复时间 |
| 为什么熔断阈值选 500ms | 本地下单链路正常 RT 在 30ms 量级，500ms 已经是一个数量级的劣化，再高就失去了提前止损的意义；这个值可以通过 `SLOW_CALL_MILLIS` 调整 |
| 熔断后怎么恢复 | 10s 窗口结束后进入半开：放一个请求过去，成功则关闭熔断，失败则继续打开。实测恢复后首次请求 30ms 返回 201 |
| 超时为什么设 1500ms | 正常 RT 30ms，1500ms 是 50 倍冗余，足够覆盖网络抖动；同时小于上游网关的读超时，保证失败发生在调用方而不是被网关截断 |
| 库存不足为什么不算熔断 | 业务结果不是技术故障，若计入会让用户连续超量下单把库存服务“熔断”，属于典型误用；代码里用 `exceptionsToIgnore` 显式排除 |
