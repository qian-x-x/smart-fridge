## 2. 事务设计

### 2.1 为什么必须是两个库

库存放 `stock_db.stock_item`，订单放 `order_db.order_record`，两者在同一个 MySQL 实例（`mysql-trade`）但**不同 schema、不同数据源**：

- 单库单表的话，一个本地事务就能保证一致性，Seata 没有存在意义；
- 分库后，"扣库存"与"写订单"是两个独立的本地事务，中间任何一步失败都会留下不一致，这才需要全局事务。

选同一实例不同库，是为了在不增加运维成本的前提下拿到真实的跨库场景；生产上如果两个库在不同实例，AT 的行为完全一致。

### 2.2 谁发起、谁参与

| 角色 | 服务 | 说明 |
| --- | --- | --- |
| TM（事务发起方） | `order-service` | `@GlobalTransactional` 开启全局事务，决定提交或回滚 |
| RM（分支参与方） | `order-service` | 订单表的 `INSERT` 注册为分支，lockKey `order_record:1` |
| RM（分支参与方） | `stock-service` | 库存表的 `UPDATE` 注册为分支，lockKey `stock_item:APPLE` |
| TC（协调者） | `seata-server` 2.1.0 | file 存储，`smart-fridge-tx-group` 分组 |

### 2.3 一阶段与二阶段的实际行为

这是本轮最值得讲清的一点：**两个分支走了不同的回滚路径**。

```
一阶段：各分支执行本地事务并提交，同时把前后镜像写入各自库的 undo_log，向 TC 注册分支
二阶段：TC 根据全局结论通知各分支 commit（删 undo_log）或 rollback（用 undo_log 还原）
```

回滚演示中的真实行为：

| 分支 | 一阶段状态 | 回滚时发生了什么 |
| --- | --- | --- |
| 订单 `INSERT` | **本地事务未提交**（异常在同一个本地事务内抛出） | Spring 本地事务直接回滚，该分支根本没注册到 TC，没有 undo_log |
| 库存 `UPDATE` | **已提交**（Feign 调用返回时 stock 的本地事务已结束） | TC 下发 `BranchRollbackRequest`，stock 用 undo_log 把 `stock` 从 95 还原为 98，然后删除 undo_log |

所以演示时能同时看到两种回滚：**未提交的本地回滚** 与 **已提交分支的二阶段回滚**。库存能还原，唯一的解释就是 Seata 起了作用。

> 会被追问的一点：为什么订单侧没有 undo_log 回滚记录？
> 因为它的本地事务在异常时还没提交，Seata 不需要为它做二阶段。如果订单也在一阶段提交（例如放在独立事务里先落库），它同样会被 TC 回滚——AT 的回滚依据是 undo_log，与分支是否在同一个服务无关。

## 3. 实现

### 3.1 库存服务：内存改为数据库

`stock_item(sku, name, stock, updated_at)`，扣减用一条带条件的 UPDATE 完成"判断 + 扣减"：

```sql
UPDATE stock_item SET stock = stock - ?, updated_at = ?
WHERE sku = ? AND stock >= ?
```

- 影响行数为 0 时再回头区分"商品不存在"（404）与"库存不足"（409）；
- 方法上 `@Transactional` 声明本地事务。Seata 代理数据源后，这条连接加入全局事务，本次扣减成为分支事务。

### 3.2 订单服务：先写订单，再调库存

```java
@GlobalTransactional(name = "order-create-tx", rollbackFor = Exception.class)
@Transactional(rollbackFor = Exception.class)
@SentinelResource(value = "order-create", blockHandler = "onRateLimited")
public OrderResult create(CreateOrderRequest request) {
    orderRepository.insertPending(orderId, request.sku(), request.quantity());  // 1. 写订单 PENDING
    StockResult stock = stockGateway.deduct(...);                              // 2. 远程扣库存
    if (!stock.ok()) throw ...;                                                // 3. 失败抛异常，触发全局回滚
    if (failAfterDeduct) throw ...;                                            // 4. 演示：扣减成功后主动失败
    orderRepository.markCreated(orderId);                                      // 5. 成功才标记 CREATED
}
```

两个关键点：

1. **失败必须抛异常，不能返回失败值**。全局事务只对异常回滚；如果库存不足时返回一个 `StockResult.failure`，已经写入的订单会被正常提交。
2. **`@Transactional` 不能省**。`@GlobalTransactional` 只开启全局事务，本地事务边界仍要由 `@Transactional` 声明，否则每条 SQL 自动提交，undo_log 与业务提交不在同一个本地事务里。

### 3.3 XID 传播

`SeataFeignConfig` 显式把 `RootContext.getXID()` 写进 `TX_XID` 请求头：

```java
String xid = RootContext.getXID();
if (xid != null && !xid.isEmpty()) template.header(RootContext.KEY_XID, xid);
```

Seata 与 OpenFeign 的自动集成在多数版本可用，但这里显式写一遍：一旦自动配置因版本调整失效，表现是"库存扣了但回滚不了"，而且不报错，排查成本极高。显式拦截器让 XID 传播成为可读代码。

### 3.4 表结构

`infra/mysql/trade/002_trade_tables.sql`：

- `stock_db.stock_item`、`stock_db.undo_log`；
- `order_db.order_record`、`order_db.undo_log`；
- 脚本显式 `SET NAMES utf8mb4`（见 4.1）；
- 种子数据用 `INSERT IGNORE`：脚本重复执行时不能把已扣减的库存重置回初始值。

`undo_log` 是 AT 的回滚依据，**每个被代理的数据源都要有一份**，缺了会在回滚时报 `undo_log table not exist`。

## 4. 验证

### 4.1 真实环境发现并修复的问题

1. **商品名双重编码**：建表脚本用 `docker exec mysql < file` 执行时，客户端字符集是 latin1，把 UTF-8 字节当 latin1 再编码，`云南小番茄` 存成 `äº‘å—å°ç•ªèŒ„`（HEX 为 `C3A4C2BA...`）。修复：脚本首行加 `SET NAMES utf8mb4;`，并重新写入三行商品名。这个问题不会报错，只会在接口里看到乱码，属于容易带进答辩的坑。
2. **首次打包失败**：Seata 依赖的 Netty 带 `netty-resolver-dns-native-macos:osx-aarch_64` 分类器，离线仓库没有该 artifact。联网补一次即可，之后离线可用。
3. **断言前提写错**：最初设计了"回滚进行中能查到 PENDING 订单"，实测查不到——因为订单插入在未提交的本地事务里，外部连接在 READ COMMITTED 下不可见。这不是 bug，而是 AT 一阶段的正常表现，断言已改为准确描述（见 4.3 第 12 项）。

## 5. 答辩话术

| 问题 | 回答要点 |
| --- | --- |
| 为什么用 AT 而不是 TCC / SAGA | AT 对业务无侵入，只要求数据源被代理、每个库有 undo_log；本项目是"扣库存 + 写订单"这种短事务，AT 足够且代码量最小。TCC 要写 try/confirm/cancel 三套接口，SAGA 要写补偿，对这个业务是过度设计。 |
| AT 的一阶段做了什么 | 解析 SQL、查前镜像、执行业务 SQL、查后镜像、把前后镜像写进 undo_log、向 TC 注册分支、提交本地事务并释放本地锁。 |
| 二阶段回滚怎么还原 | 用 xid + branchId 找到 undo_log，比对当前数据与后镜像（校验脏写），一致则用前镜像反向生成 SQL 执行，最后删 undo_log。 |
| 全局锁在哪、锁多久 | 一阶段结束后分支持有 TC 的全局锁直到全局事务结束，本地锁已释放。所以 AT 保证的是全局写隔离，不是读隔离。 |
| 库存不足为什么也要走全局事务 | 因为订单已经先写入了。如果不回滚，就会出现"有订单没库存"。这里的正确做法是让异常触发全局回滚，而不是返回失败值。 |
| 如果 TC 挂了会怎样 | file 模式下 TC 是单点，挂了之后新事务无法开启（客户端拿不到 XID）。生产要部署 TC 集群 + 数据库存储模式，本轮只做单机演示。 |
| undo_log 会不会一直涨 | 正常提交和回滚都会删除。长时间不删说明有分支卡住，需要看 TC 的重试记录。可以定期清理 `log_created < now() - interval 7 day` 的残留行。 |

## 6. 未覆盖

- **TC 高可用**：单机 file 存储，没有集群与故障切换演示。
- **全局事务超时与重试**：默认 60s，没有做"TC 不可达"的降级演示。
- **悬挂与空回滚**：需要人为制造"回滚请求先于一阶段到达"，本轮未构造。
- **幂等**：`order_record` 有唯一键，但下单接口没有用 `requestId` 去重，重复提交会生成两笔订单（业务上应由前端/网关幂等键解决）。
- **压测**：没有测全局事务的吞吐，AT 的全局锁会成为写热点，这个结论只有压测能给数据。
