# 过期清理、食材编辑与局域网接入审查（2026-11-06）

## 1. 本轮范围

来自使用反馈的四点：

| # | 反馈 | 处理 |
| --- | --- | --- |
| 1 | 过期食材缺一键清理 | 新增 `POST /api/v1/fridges/{fridgeId}/discard-expired` 与确认弹层 |
| 2 | 加购后不能改库存信息（例如把西兰花从水果改成蔬菜） | 新增「修改分类与信息」入口，复用新增表单为编辑模式，走 `PUT /api/v1/foods/{foodId}` |
| 3 | 服务只能在 localhost 访问 | Web 改为同源代理 API，补局域网端口方案与文档 |
| 4 | 运营后台接口是否还没做 | 核查结论：确实没做，见第 6 节 |

## 2. 后端

### 2.1 过期食材批量清理

- `POST /api/v1/fridges/{fridgeId}/discard-expired`，返回 `{count, skipped, foods[]}`。
- 过期判定在服务端按**冰箱时区**、用服务器时钟计算 `expires_on < today`。今天到期的不算过期，仍可食用；客户端时钟错误无法清空新鲜库存。
- 逐条软删除（`status = 'DISCARDED'`，数量归零），每条写 `DISCARD` 流水，备注为「过期清理」，因此清理结果仍可像普通丢弃一样在时间线里逐条撤销。
- 被丢弃的食材不再是 `ACTIVE`，所以视图快照在删除**之前**构造，避免删除后读不回来。
- 删除用行内 `version` 做条件更新：若某条被并发修改则跳过该条（计入 `skipped`），不会让整批失败。
- 权限：仅 `OWNER` / `EDITOR`，`VIEWER` 返回 403；未知冰箱 404。

### 2.2 食材编辑

`PUT /api/v1/foods/{foodId}` 在本轮之前已存在且支持分类、数量、单位、分区、日期与标签，缺的只是客户端入口。本轮只补了客户端，并复核了三条约束：

- `version` 不一致返回 409（乐观锁），错误文案「食材已被其他成员更新，请刷新后重试」。
- 目标分区必须属于该冰箱、容器必须属于该分区。
- 到期日不得早于生产日。

`V3` 迁移的 `UPDATE` 流水保持原样，编辑会写一条 `UPDATE` 记录（不可撤销，因为原字段不足以还原）。

## 3. 客户端

### 3.1 编辑入口

- 食材详情弹层新增「修改分类与信息」，打开与新增共用的表单（`_FoodFormSheet`）。
- 表单预填名称、分类、数量、单位、分区、生产/到期日期；分类仍是 12 项预设，避免自由输入再次写错。
- 未改分区时保留原容器，改分区才改用新分区的第一个容器（否则容器不属于新分区会被后端 409）。
- 保存成功后表单与详情弹层一起关闭，回到首页并刷新工作区，提示「食材信息已更新」。
- 编辑不进入详情弹层的 `busy` 状态：之前 `_run` 会点亮无限动画的进度条，导致嵌套表单打开时界面永不静止（测试里表现为 `pumpAndSettle` 超时），改为按返回值决定是否关闭详情。

### 3.2 一键清理入口

- 库存面板在存在已过期食材时显示「清理 N 份过期食材」，点击弹出确认层，列出每一条的名称、分类、数量与过期天数。
- 确认后调用批量接口，提示「已清理 N 份过期食材」；只读成员与演示模式不展示可写入口，直接调用也会被拦截并提示。
- 清理后按钮自动消失（过期数归零）。

## 4. 局域网接入

### 4.1 四个改动

1. **Web 同源代理**：`infra/web/nginx.conf` 让 nginx 托管 Flutter 产物并把 `/api/` 反代到 `sf-gateway:8080`。浏览器只访问页面所在源，不再跨源请求 8080。
2. **客户端地址推导**：`AppConfig.apiBaseUrl` 在 Web 上返回 `Uri.base.origin`，因此在 `127.0.0.1`、`localhost` 或任意局域网地址打开都能自动指向同一源的 API。原生端保留 `API_BASE_URL` 覆盖。
3. **网关 CORS**：改用 `allowed-origin-patterns`，覆盖 `localhost:*`、`127.0.0.1:*`、`192.168.*`、`10.*`、`172.*`。运营端从局域网 5173 访问时仍然可用。
4. **会话存储**：Web 不再走 `flutter_secure_storage`，改用条件导入的 `shared_preferences`。原因是 secure storage 在 Web 依赖 WebCrypto，而 `http://` 页面不是安全上下文，`crypto.subtle` 不可用会让**登录静默失败**（接口 200、页面停在登录页）。原生端继续用系统 keystore。

### 4.2 容器端口

Docker Desktop for Windows 只把 `-p` 端口发布到 `127.0.0.1`，局域网设备连不上（实测容器内访问宿主 LAN IP:8080 失败，`netstat` 也看不到 `0.0.0.0` 监听）。两种可用方案：

| 方案 | 命令 | 说明 |
| --- | --- | --- |
| 系统端口代理（推荐） | `scripts/Enable-LanAccess.ps1` | 需管理员；把 `0.0.0.0:3000` 转发到 `127.0.0.1:3030`，并放行防火墙；重启后仍有效 |
| 用户态转发（免提权） | `python scripts/lan-bridge.py 3000=3030` | 普通权限即可，进程退出后失效 |

因此 Web 容器改发布到 `3030`，对外统一用 `3000`，两者不冲突。

### 4.3 实测

- 页面：`http://10.66.46.139:3000`，登录后 `login → families → fridges → foods` 四条请求全部 200，会话写入 localStorage。
- 容器内（模拟外部设备）访问 `10.66.46.139:3000` 返回 `HTTP/1.1 200 OK`。
- 桌面 UI 验收脚本整体跑在局域网地址上，见第 5 节。

## 6. 运营后台现状

**结论：运营后台接口确实还没做。** 具体现状：

- `apps/admin-web` 只有 5 个页面（看板、商品、订单、菜谱、登录），全部使用硬编码的示例数组，页面里明确写着「示例 SKU」「示例订单」「示例发布状态」，没有任何 `http` 调用。
- `src/api/http.ts` 只建了 axios 实例与令牌头，没有接口函数；`src/api/index.ts` 只再导出 `http`。
- 后端 7 个服务里没有任何 `/api/v1/admin/**` 路由，也没有管理员角色或权限模型（`app_user.role` 只有 `USER`）。
- 现有可复用的接口只有商品/补货与订单的骨架路由（`stock-service`、`order-service`，仅健康检查与占位实现）。

要做成可用的运营后台，至少需要：

1. 管理员身份与鉴权（角色或独立表 + 网关白名单）。
2. 商品/SKU 的增删改查与库存调整接口（现在 `stock-service` 没有持久化）。
3. 订单查询与状态流转接口（`order-service` 同样只有骨架）。
4. 菜谱审核/发布接口（`recipe-service` 目前只有目录查询）。
5. 看板统计聚合接口（订单量、GMV、临期预警）。
6. 运营端把示例数组替换为真实请求，并补登录与权限拦截。

这部分工作量明显大于本轮的三项修复，未纳入本轮，需要单独立项。

## 7. 已知限制

- 今天到期的食材不会被一键清理，需要用户自行处理或等次日。
- 清理不支持按分区筛选，一次处理整台冰箱；需要更细粒度时用「全部食材与筛选」逐条丢弃。
- 局域网走 `http`，Web 端会话存在 localStorage；若要回到系统级安全存储，需要给站点配 https（自签证书需在手机上手动信任）。
- Docker Desktop 的端口限制属于环境问题，替换为 Linux 主机或 Kubernetes 时可直接用 `-p` 暴露。
- UI 验收脚本依赖固定视口坐标（1414×807），分辨率变化需重新标定。
