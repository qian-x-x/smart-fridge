# 家庭协作与工作区切换设计

## 状态

- 日期：2026-10-29
- 状态：已确认，待用户审阅
- 所属阶段：S2 家庭协作第一纵切

## 背景

当前认证家庭服务支持注册、登录、家庭创建、家庭列表和家庭详情，数据库已有家庭邀请码和成员角色。客户端可以创建家庭，但冰箱工作区始终选择家庭列表第一项，也缺少邀请码加入、成员治理、所有权转交和手动切换家庭的能力。

本纵切补齐家庭协作和工作区切换。无家庭或无冰箱时的首次配置流程不属于本纵切，留到下一个纵切完成。

## 目标

- 已登录用户可以通过 8 位家庭邀请码加入家庭。
- 新成员默认角色为 `VIEWER`。
- 家庭成员可以查看成员列表。
- `OWNER` 可以调整普通成员角色、移除成员并转交所有权。
- 客户端可以显式选择家庭，并在重新打开应用后恢复选择。
- 冰箱和菜谱统一使用当前选中的家庭。

## 非目标

- 邮件、短信或链接邀请。
- 邀请码轮换或撤销。
- 成员主动退出家庭。
- 多个家庭拥有者。
- 无家庭或无冰箱时的首次配置引导。
- WebSocket 实时推送家庭成员变化。

## 领域规则

### 邀请与加入

- 邀请码继续使用 `family.invite_code`，输入时去除首尾空白并转换为大写。
- 已认证用户可以凭有效邀请码加入家庭，新增成员角色固定为 `VIEWER`。
- 用户已经是该家庭成员时，加入接口幂等返回家庭和当前角色。
- 用户已经属于其他家庭不影响加入新家庭，因为系统支持多家庭。
- 无效邀请码返回 `404 NOT_FOUND`，提示“邀请码无效”。

### 成员角色

- 每个家庭只有一个 `OWNER`，由 `family.owner_user_id` 和 `family_member.role` 共同表示。
- 通用角色调整接口只允许把普通成员设置为 `EDITOR` 或 `VIEWER`。
- 通用成员接口不能修改或移除 `OWNER`。
- `OWNER` 不能通过通用接口移除自己。
- `OWNER` 可以将所有权转交给当前角色为 `EDITOR` 的成员。
- 所有权转交后，目标成员变为 `OWNER`，原拥有者变为 `EDITOR`。
- 所有权转交必须同时更新 `family.owner_user_id` 和双方成员角色。

### 家庭选择

- 当前家庭只保存在客户端，不增加服务端“当前家庭”字段。
- 选择按用户隔离保存，重新打开应用后优先恢复。
- 保存的家庭仍属于当前用户时继续使用。
- 保存的家庭已失效时回退到家庭列表第一项并覆盖本地保存值。
- 家庭列表为空时没有当前家庭。
- 创建或加入家庭成功后自动选中该家庭。

## 架构

继续使用 `auth-family-service` 作为成员关系的唯一事实来源，不新增服务或数据表。客户端继续通过 Gateway `8080` 访问接口。

成员治理操作使用 `JdbcTemplate` 事务。涉及角色或所有权变更的操作先锁定家庭行，再校验当前用户与目标成员，以避免角色调整、移除和所有权转交并发造成不一致。

主要分层：

- `FamilyController`：HTTP 参数接收和响应。
- `FamilyService`：加入、授权、角色规则和事务编排。
- `FamilyRepository`：家庭、成员和用户的查询及更新。
- Flutter `FamilyController`：家庭列表、加入/创建、当前家庭选择与持久化。
- Flutter `FamilyMembersController`：当前家庭成员列表和成员治理。
- Flutter `FridgeWorkspaceController`：监听当前家庭并加载对应冰箱。

## API 契约

所有接口都要求有效 access token。

| 方法 | 路径 | 权限 | 成功响应 |
| --- | --- | --- | --- |
| `POST` | `/api/v1/families/join` | 已登录用户 | `200`，`FamilyView` |
| `GET` | `/api/v1/families/{familyId}/members` | 家庭成员 | `200`，`FamilyMemberView[]` |
| `PATCH` | `/api/v1/families/{familyId}/members/{userId}` | `OWNER` | `200`，更新后的 `FamilyMemberView` |
| `DELETE` | `/api/v1/families/{familyId}/members/{userId}` | `OWNER` | `204` |
| `POST` | `/api/v1/families/{familyId}/transfer-owner` | `OWNER` | `200`，更新后的 `FamilyView` |

### 加入家庭

请求：

```json
{
  "inviteCode": "ABCD2345"
}
```

响应数据使用现有 `FamilyView`，其中 `currentUserRole` 为新成员当前角色。

### 成员列表

`FamilyMemberView` 字段：

- `userId`
- `username`
- `displayName`
- `role`
- `joinedAt`
- `currentUser`

成员列表按角色优先级和加入时间稳定排序，`OWNER` 始终在前。

### 调整角色

请求：

```json
{
  "role": "EDITOR"
}
```

只接受 `EDITOR` 和 `VIEWER`。

### 转交所有权

请求：

```json
{
  "targetUserId": 42
}
```

目标用户必须是该家庭的 `EDITOR`。

## 错误契约

沿用统一响应结构和现有 `ErrorCode`：

- 未登录：`401 UNAUTHORIZED`
- 家庭成员但没有 `OWNER` 权限：`403 FORBIDDEN`
- 家庭不存在、不是家庭成员或邀请码无效：`404 NOT_FOUND`
- 非法角色、操作 `OWNER`、移除自己、非 `EDITOR` 目标或并发所有权冲突：`409 CONFLICT`
- 请求字段校验失败：`400 VALIDATION_ERROR`

客户端直接展示后端提供的用户可读消息，不清空当前有效页面状态。

## 客户端交互

家庭页：

- 家庭卡片显示选中状态，点击后切换当前家庭。
- 提供“加入家庭”入口和邀请码输入弹窗。
- 选中家庭后展示成员列表和当前用户角色。
- `OWNER` 可以打开成员操作面板调整角色或移除成员。
- 所有权转交只允许选择 `EDITOR`，执行前二次确认。
- 当前用户、`OWNER` 和不允许执行的操作显示明确状态。

家庭页之外：

- 冰箱页依赖当前家庭，不再自动使用列表第一项。
- 家庭切换后自动重新加载冰箱。
- 菜谱匹配基于刷新后的冰箱快照。
- 没有家庭时提示创建或加入家庭。
- 当前家庭没有冰箱时提示切换家庭，不提供创建冰箱入口。

## 持久化

使用现有 `shared_preferences` 依赖保存选择，键按用户隔离，例如：

```text
smart_fridge.selected_family.<userId>
```

切换家庭成功后立即写入。读取到无效家庭 ID 时回退第一项并覆盖保存值。

### 后端

新增家庭协作集成测试，覆盖：

## 验收标准

- 用户可以使用邀请码加入家庭，并默认显示为 `VIEWER`。
- 家庭页可以切换多个家庭，重启应用后选择仍有效。
- 冰箱和菜谱会随当前家庭切换。
- `OWNER` 可以完成普通成员角色调整和移除。
- `OWNER` 可以把所有权转交给 `EDITOR`，原拥有者变为 `EDITOR`。
- 所有权限限制同时由后端和客户端表达，客户端不承担最终授权责任。
- 后端测试、Flutter 测试和 `dart analyze lib test` 全部通过。
- OpenAPI、开发状态和运行手册同步更新。
