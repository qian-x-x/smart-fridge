# 乙方开工评审与交付边界

## 评审结论

V1.2 的技术路线完整且基本自洽，可以作为 S0 需求冻结的工作底稿。项目包含 Flutter 双端用户端、Vue 运营后台、7 个后端服务、完整中间件和课程证据链，实质上是端到端外包交付，而不是单一 App 页面项目。

乙方可以进入需求澄清和方案细化，但在以下条件未书面锁定前，不宜承诺固定总价、固定日历工期或最终验收通过时间：

- V1.2 尚未签署，文件自身仍标记为“待双方书面确认”。
- P1 被描述为“交付前应完成”，合同效力需要明确。
- 内容素材数量、授权责任和审核流程尚未落到交付计划。
- 性能指标没有完整绑定验收硬件、网络、数据集和测量脚本。
- 7 个服务、双端 Flutter 和课程治理组件没有对应的团队分工与排期。

## 乙方理解的项目范围

### 业务范围

- 注册、登录、JWT、平台角色、家庭角色和家庭邀请。
- 冰箱分区、隔层、抽屉、常温储物筐及其 2.5D 可视化。
- 食材和调料的增删改查、移动、使用、丢弃、恢复、筛选和临期计算。
- 基于食材的菜谱推荐、缺少项计算、做饭确认、原子扣减和烹饪记录。
- 补货清单、商品库存、优惠券、模拟支付、订单查询与取消。
- 临期、家庭变更和订单状态的异步通知。
- 用户管理、菜谱、商品、库存、优惠券、订单和数据看板后台。
- Docker Compose、初始化数据、演示账号、文档和验收证据。

### 不可降级的交付门槛

| 门槛 | 乙方需要交付的可验证结果 |
| --- | --- |
| 2.5D 视觉 | 外壳、腔体、储物层、贴纸层和信息层独立实现；至少一组 250 至 450 毫秒的滑出或展开交互 |
| 家庭协作 | 两台在线客户端在 2 秒内同步同一次食材变更；后端角色校验失败返回 403 |
| 做饭扣减 | 确认前显示扣减量；确认后只扣一次，操作、烹饪记录和库存数量一致 |
| 补货事务 | 库存不足时订单不成功，库存和优惠券没有部分提交 |
| 微服务证据 | 7 个服务在 Nacos 可发现；Gateway、OpenFeign、Sentinel、Seata、SkyWalking、RocketMQ 和 MinIO 均有真实业务证据 |
| 双端交付 | Android release APK 可安装，Flutter Web 可启动，两端共享同一账户数据 |
| 降级路径 | 素材或 WebSocket 异常时给出明确状态；表格视图仍可查看完整食材数据 |

## 主要交付风险

### 综合复杂度被单页原型低估

文档包含 2.5D 自绘交互、家庭实时协作、菜谱推荐、库存扣减、优惠券、模拟支付、运营后台、双端 Flutter、7 个服务和 10 余项中间件集成。任一课程组件的“真实业务证据”都需要开发、联调和演示材料共同支持。

乙方应在 S0 建立需求、接口和验收编号的追踪矩阵，避免 S5 才集中补齐证据。

### 内容生产不是附属工作

交付要求包括 60 张版权清晰贴纸、80 道菜谱、30 个商品、菜谱封面、2.5D 分层插画及完整素材授权清单。贴纸还要求透明背景、512 × 512 像素建议尺寸和单张不超过 200 KB。

乙方报价与排期必须明确：

- 贴纸和插画是原创交付、采购授权还是由甲方提供。
- 菜谱文字、图片、商品图和字体由谁提供并承担权利瑕疵责任。
- 谁进行视觉验收，返工轮次如何计算。
- 参考小红书内容只能提供功能灵感，不能直接复用原图、文字、界面或冰箱造型。

### 课程组件必须进入真实业务流

Nacos、Gateway、Sentinel、Seata、SkyWalking 和 RocketMQ 不能在 README 或演示页面中“声明使用”。甲方要求现场演示控制台、日志、回滚或 Trace 证据。

乙方需要在架构评审时确定每一项证据的操作步骤、保存格式和负责人。S1 就要完成可重复的本地基础设施底座，不能等业务结束后回补。

### 性能指标需要统一测量口径

文档中的 3 秒冷启动、4 秒 Web 首次可见、2 秒实时同步、1000 条列表 1.5 秒和下单 p95 3 秒，缺少全部测量细节。

建议在 S0 补充：

- “冷启动”和“首次可见”的起止事件。
- 中端 Android 的明确型号、系统版本和硬件配置。
- Flutter 运行时是否计入 Web 首次下载时间。
- 本地有线网络的速度、延迟和丢包基准。
- 1000 条种子数据的字段分布、并发数和是否冷缓存。
- 下单 p95 的样本数、并发模型、成功率和失败注入方式。
- 性能脚本、原始结果和复测环境。

### 16 GB 验收机资源压力

文档要求 Windows 11、16 GB 内存同时运行 Flutter 开发或演示、7 个 Java 服务、2 个 MySQL、Redis、MinIO、RocketMQ、Seata、Sentinel、SkyWalking 和浏览器。该配置的实际可用内存与磁盘吞吐可能影响启动时间和稳定性。

乙方应提供 core/full 两组 Compose、资源上限和启动顺序，但最终仍须在甲方指定机器上实测 full 环境。若验收环境无法承载文档定义的全量组件，应在 S0 形成书面调整，而不是在验收时临时解释。

### 干净环境与网络条件未定义

项目要求从仓库和镜像说明启动，不能依赖开发者缓存。需要进一步确认：

- 是否允许验收机联网拉取固定版本镜像和 Maven、pub、npm 依赖。
- 是否需要提供离线镜像包或依赖缓存。
- Docker Desktop、WSL、端口占用和防火墙由谁配置。
- 演示数据、对象存储桶和 Nacos 配置是否由初始化脚本自动创建。

### 权限与访问责任

K-04 要求甲方第一天拥有只读权限。当前私人仓库已建立，但尚未获得甲方 GitHub 账号，因此不能完成协作者授权。

乙方建议明确：

- 甲方使用哪个 GitHub 账号。
- 分支策略、代码评审和合并权限。
- 验收通过后“完整控制权”的移交方式。
- 合同终止或人员变动时，组织和仓库权限如何回收。

## P0 与 P1 的合同处理建议

文档将 P0 定义为期末验收必须有，将 P1 定义为交付前应完成。两种表述在合同执行上可能同时构成必交项。

建议双方使用以下三档，不用“待定”字样进入开发：

| 档位 | 建议含义 | 变更规则 |
| --- | --- | --- |
| 验收必交 | AC-01 至 AC-15 及支撑其运行的 P0 功能 | 缺失即不进入验收 |
| 交付必交 | 文档明确的 P1 功能 | 可单独缺陷跟踪，但影响总交付 |
| 后续范围 | 文档未列明的新增功能 | 先评估工期和费用，再书面确认 |

若甲方希望把任何 P1 降为可选，应在 S0 删除或改写原文，不要只依赖口头确认。

## 建议的乙方工作方法

1. 先完成 S0：用户故事、页面清单、接口草案、ER 图、架构图、原型和验收矩阵一次冻结。
2. 用验收编号贯穿接口、开发任务、测试用例和演示脚本；每个 P0 至少映射一条自动化或可复现测试。
3. 每周演示可运行增量，同时归档运行日志、截图和未关闭缺陷。
4. 中间件在业务功能落地时同步接入，不将控制台证据集中在最后制作。
5. 素材、依赖和字体在入库时登记来源、许可证和审核人。
6. 发布前执行从干净环境的部署演练，并保存失败、降级和回滚场景。

## 开工前书面疑问清单

以下问题应在乙方签署排期或报价前得到结论：

1. V1.2 是否为最终冻结版本，甲乙双方由谁签署，何时生效？
2. P1 是否全部属于交付必交项，哪些允许延期？
3. 60 张贴纸、80 道菜谱、30 个商品和所有图片由哪一方生产与授权？
4. “中端 Android 设备”的具体基准型号是什么？
5. 首次 Web 可见时间和冷启动时间的起止点如何定义？
6. 下单 p95 的并发量、请求模型、样本量和失败注入规则是什么？
7. 验收机是否可以联网，是否需要离线镜像和依赖缓存？
8. 16 GB 验收机能否支持 full Compose 全量运行，是否有最低 CPU 和磁盘要求？
9. 7 个服务的边界和端口是否可直接冻结，允许合并的条件由谁批准？
10. 甲方 GitHub 账号是什么，谁负责只读邀请和最终权限移交？
11. 最终验收人、每周演示时间和证据保存方式由谁确定？
12. 严重缺陷、一般缺陷和视觉返工的关闭标准及复验轮次如何约定？

- iOS IPA 与桌面安装包。
- 未书面确认的新功能。
