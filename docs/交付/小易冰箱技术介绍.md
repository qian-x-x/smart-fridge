# 小易冰箱技术介绍

面向技术新手的功能与实现说明

版本日期：2026年11月9日

小易冰箱是一款家庭食材管理作品。用户可以创建或加入家庭，把食材放进虚拟冰箱，查看临期食材，按现有食材寻找菜谱，并在做饭后扣减数量。本书从这些操作出发，解释每项技术解决什么问题，以及对应代码在哪里。

本版本的电脑端真实接口与 Web 验收已通过。Android 安装包已构建，真机联网和触控尚未验收。家庭补货指食材入库，用户端没有商城、购买、支付或订单功能。仓库保留的 order、stock 和管理端订单页属于历史技术示例。

建议阅读顺序：先看第1至4章认识全貌；重点阅读第9至14章理解课程中间件如何落地；最后按第20章的路线操作和讲解。每章中的路径都相对于项目根目录，接手人可以按路径找到实现。

## 1 作品功能与当前边界

### 先从使用者的角度认识作品

假设一家人准备做晚饭。成员打开冰箱首页，看见家里有哪些食材、放在哪个分区、哪些快过期。新买回的鸡蛋需要手动录入；用掉两个鸡蛋后，成员记录使用数量。另一位成员可以在再次加载时看到最新库存。系统没有连接实体冰箱传感器，也不会自动识别采购结果。

| 用户操作 | 当前作品的实际行为 |
| --- | --- |
| 注册和登录 | 创建账号，验证密码，取得会话令牌 |
| 创建家庭 | 同时创建家庭、OWNER成员、默认冰箱、四个分区和六个容器 |
| 邀请家人 | 通过邀请码加入，OWNER调整成员权限 |
| 食材管理 | 新增、编辑、筛选、移动、使用、丢弃和过期清理 |
| 查看记录 | 查询操作时间线，对支持的操作执行撤销和恢复 |
| 看菜谱和做饭 | 匹配已有食材，确认后扣减选定食材并留下做饭记录 |

### 页面端和服务不是一回事

项目有两个前端工程：Flutter用户端和Vue管理端。Flutter可以构建为Web网页或Android应用，属于同一套客户端的两个运行形式。Vue管理端目前是静态原型，仪表盘、菜谱、库存和订单页面使用示例数据，尚未接入真实管理员权限或业务API。

日常运行四个后端应用：gateway、auth-family、fridge、recipe。代码里另外保留stock和order两个历史服务，需要显式选择才启动。不能因为仓库里有订单代码，就认为用户补货会下单。

### 还没有完成的能力

WebSocket即时推送、RocketMQ通知、MinIO业务上传、菜谱收藏、独立做饭历史页面和冰箱布局配置尚未完成。做饭记录查询API已经存在，独立历史页面尚未做。Android正式签名、真机验收和持续容量压测也待完成。

## 2 一次操作经过哪些地方

### 先认识五个常用词

前端是用户看见并点击的界面；后端是在服务器上执行规则的程序；API是前后端约定的调用入口；数据库长期保存数据；中间件为多个程序提供公共能力，例如寻找服务、协调事务和收集追踪。

### 创建家庭的实际路线

| 顺序 | 谁在工作 | 具体做什么 |
| --- | --- | --- |
| 1 | Flutter | 用户输入家庭名称，生成requestId，发出HTTP请求 |
| 2 | Gateway | 检查JWT身份，把请求转给auth-family服务 |
| 3 | auth-family | Sentinel检查流量；开启Seata全局事务；写家庭和OWNER关系 |
| 4 | Nacos与Feign | 按fridge-service名称找到实例，调用创建冰箱接口 |
| 5 | fridge | 向auth校验家庭权限；写默认冰箱、四区和六个容器 |
| 6 | Seata与两个服务 | 协调全局提交或回滚，确认后返回家庭和冰箱编号 |
| 7 | Flutter | 选中新家庭，加载新冰箱；SkyWalking记录后端调用过程 |

这里的HTTP可以理解为“按约定地址发送一份请求，再接收结果”。JSON是请求和响应中使用的数据格式。例如创建家庭提交名称和请求编号，而不是把整个数据库传给后端。

### 四个服务各自负责什么

gateway是统一入口，端口8080；auth-family负责账号、家庭和成员，端口8081；fridge负责冰箱、食材、操作和做饭，端口8082；recipe提供菜谱目录与详情，端口8083。端口可以理解为同一台电脑上不同程序的门牌号。

逻辑上三个业务分别拥有auth_db、fridge_db、recipe_db。当前它们可以放在同一个MySQL实例里，仍然由各自服务管理。服务分库不等于一定需要三台电脑。

这些中间件直接服务于用户点击的功能，但主要运行在后端。用户通常只看到成功、失败或重试提示，不需要看到Feign或Seata按钮。

## 5 Flutter如何组织页面

### 点击一次按钮之后发生什么

以食材入库为例。页面收集名称、数量、单位和分区，控制器进入提交中状态，仓库对象通过Dio发送API请求。后端确认保存后，控制器重新获得库存数据，Riverpod通知界面更新。食材清单、数量摘要和三维场景读取同一份快照，因此能保持一致。

这里的仓库Repository是一层数据访问代码，用于把“页面想做什么”和“具体HTTP怎么发送”分开。它不等于MySQL数据库，也不会自动在本机保存一份服务器数据库。

### 四层代码分别处理什么

| 层次 | 作用 | 项目例子 |
| --- | --- | --- |
| presentation | 显示内容、收集输入、展示错误 | family_action_dialog.dart |
| application | 组织操作步骤和页面状态 | family_controller.dart |
| domain | 描述业务对象 | family_info.dart、food相关模型 |
| data | 发送请求、解析响应、保存选择 | family_repository.dart、api_fridge_repository.dart |

登录状态、家庭状态和冰箱状态存在依赖关系：用户变化后，需要重新确定可见家庭；家庭变化后，需要重新加载对应冰箱。控制器在异步返回时检查上下文，防止旧家庭的慢请求覆盖新家庭画面。

### 页面里的加载和失败也是功能

AsyncLoading表示正在加载；AsyncData表示获得数据；AsyncError表示失败。界面据此显示进度、内容或重试入口。重复提交时禁用按钮只是第一层保护，后端还需要幂等和权限检查。

创建家庭成功后直接使用服务端返回的家庭，不依赖额外一次家庭列表请求才能认定成功。若本地保存当前家庭失败，已提交的家庭仍然有效；下次可从服务端列表重新选择。

代码入口：apps/fridge-app/lib/features/family/、core/network/api_client.dart、core/router/app_router.dart。普通页面修改通常从presentation开始；排查数据问题则继续看application和data。

## 6 三维冰箱如何显示真实食材

### 三维显示和食材数据各做一件事

Web端使用Three.js建立场景、相机、灯光、门体、抽屉和简化食材模型，使用WebGL绘制。可以把Three.js理解为舞台布置工具，WebGL理解为负责绘制的浏览器能力。它们不会自动知道冰箱里有什么，必须接收后端食材数据。

Flutter加载当前家庭的冰箱快照后，将分区和食材信息传给嵌入的场景页面。场景中的几何体根据这份快照更新。用户选择分区或点击食材时，场景再把事件传回Flutter，打开对应信息或筛选状态。

### 三种交互如何实现

拖拽环绕是调整相机观察角度。射线拾取是从点击位置向三维空间发出一条数学射线，判断先碰到哪个物体。门体和抽屉动画则改变物体的旋转或位置，形成开门、关门和拉出的效果。

| 内容 | 数据来源 | 当前边界 |
| --- | --- | --- |
| 食材名称、数量和分区 | 当前家庭的后端快照 | 需要用户维护，没有摄像头自动识别 |
| 门、抽屉、灯光和材质 | 本地场景代码 | 是虚拟模型，不控制实体冰箱 |
| 储存参考温度 | 界面参考值 | 没有硬件传感器实时温度 |
| Android厨房视觉 | 参考图和Flutter界面 | 没有直接复用Web交互式三维场景 |

搜索列表只改变搜索结果，不改变完整库存。因此搜索“牛奶”时，场景仍能显示家庭全部食材。浏览器不支持WebGL时，会显示错误说明，并提供使用同一份数据的表格清单。

Three.js运行文件在web/vendor目录本地打包，附有许可证，不依赖外部CDN。场景被隐藏时暂停渲染，可以减少无用的显卡工作。

代码入口：apps/fridge-app/web/下的场景模块，以及lib/features/fridge/presentation/widgets/webgl_fridge_view_web.dart。查看原生差异时再读webgl_fridge_view_stub.dart。

## 7 登录与会话

### JWT是一张有期限的身份凭证

用户登录成功后，后端签发access token和refresh token。access token随业务请求发送，后端校验签名、有效期和令牌类型后确认身份。JWT签名用于防止内容被篡改，不能把普通JWT理解为内容经过加密。

默认access token有效期30分钟，refresh token为7天，可通过配置调整。前者用于日常访问；后者用于换取新的令牌。Flutter在access token临近过期时刷新，刷新失败则清除会话并返回登录页。

### BCrypt和Redis分别解决什么

BCrypt处理密码摘要。注册时保存摘要，登录时把输入密码与摘要匹配，数据库不需要保存明文密码。项目使用BCrypt强度12。它和JWT是两回事：BCrypt帮助验证密码，JWT帮助后续请求证明身份。

Redis保存被撤销的access token编号，并设置到令牌到期的剩余时间。登出后，网关通过认证服务检查撤销状态，旧令牌就不能继续正常使用。refresh token会话保存在MySQL，刷新时通过条件更新消费旧令牌，避免同一旧令牌无限重放。

### 会话存在哪里

| 客户端 | 当前实现 |
| --- | --- |
| Android等原生平台 | 使用flutter_secure_storage封装平台安全存储 |
| Web开发环境 | 使用shared_preferences对应的浏览器localStorage保存会话 |
| 服务端 | MySQL保存刷新会话；Redis保存access token撤销状态 |

Web开发环境支持局域网HTTP，而WebCrypto通常要求安全上下文，因此Web分支采用localStorage。它不等同于原生安全存储；正式公开部署仍需要HTTPS和完整的安全设计。本地开发密钥是示例配置，交付包不提供真实账号和已有会话。

代码入口：auth-family-service的AuthService、JwtTokenService、RefreshSessionRepository、RedisTokenRevocationService；Flutter的core/session/。测试签名APK不能代表正式上架版本。

## 8 家庭权限与数据隔离

### 登录不代表可以看所有家庭

身份验证回答“你是谁”，权限校验回答“你能操作这个家庭吗”。即使一个用户已经登录，手工把URL里的fridgeId改成别人的冰箱编号，后端也必须拒绝访问。只在页面隐藏按钮无法提供这种保护。

| 角色 | 可以做什么 |
| --- | --- |
| OWNER | 管理家庭成员、调整权限、转交所有权，并管理食材 |
| EDITOR | 查看家庭冰箱并新增、修改、使用等操作食材 |
| VIEWER | 查看家庭数据；写接口由后端返回403 |

通过邀请码加入的新成员默认是VIEWER。只有OWNER可以提升为EDITOR。转交所有权需要同时更新家庭的所有者字段和成员关系，原OWNER变为EDITOR；这些变化放在本地事务中完成。

### 食材请求如何检查归属

fridge服务先确定食材属于哪台冰箱，再确定冰箱属于哪个家庭，然后通过Feign向auth-family查询当前用户的家庭角色。FridgeAccessGuard统一这些检查，避免每个接口随意实现一套规则。更新时还要核对目标分区、容器是否属于同一台冰箱。

Gateway会清除客户端传来的伪造身份头，并根据真实令牌处理身份。它还清除客户端TX_XID，防止外部请求冒充后端分布式事务。服务端的创建入口也拒绝外来事务上下文。业务服务继续验证令牌和家庭权限，不能只相信客户端传入的userId。

### 异步页面也需要隔离

用户从家庭甲切换到家庭乙后，甲的旧请求可能才返回。控制器需要确认当前用户和家庭仍然匹配，才能更新画面。后端隔离数据，前端检查异步上下文，两者共同避免显示错家庭。

代码入口：gateway的JwtGatewayFilter；fridge的FamilyAccessService与FridgeAccessGuard；auth-family的FamilyService；Flutter的family_controller.dart与fridge_workspace_controller.dart。

## 9 Nacos发现服务和刷新配置

### 注册中心像一份正在更新的通讯录

gateway知道请求应该交给fridge-service，但不必把某个固定IP写死在路由中。服务启动后向Nacos登记名称、地址和端口；调用方按名称查询可用实例，再由LoadBalancer选择实例。项目的gateway路由使用lb://fridge-service等地址。

这对创建家庭有直接作用：auth-family通过Feign寻找fridge-service初始化冰箱；fridge回查家庭角色时同样按服务名找到auth-family。日常分组为SMART_FRIDGE，隔离验收使用独立分组，防止测试请求误入日常实例。

“使用了负载均衡组件”不等于已经证明高并发或多副本容灾。本版本日常每个服务只有一个健康实例，已验证按名称发现和调用；多实例容量和高可用没有验收。

### 配置中心像一份公共参数表

临期阈值决定“还有几天到期就提醒”。fridge-service从Nacos读取fridge-service.yaml，通过@RefreshScope刷新配置对象。默认值为3天。如果把阈值改为10天，一份5天后到期的食材就会被标记为临期；改为1天时不会。

配置键是smart-fridge.fridge.expiring-threshold-days，分组是SMART_FRIDGE。读取配置和按名称发现服务属于Nacos的两项能力，不能混为同一项功能。不要把可动态调整的服务阈值说成已经实现“每个用户独立设置阈值”的页面。

### 怎样演示

先在Nacos实例列表查看四个真实业务服务，再在用户端打开同一份有明确到期日期的食材。按运行手册发布两个阈值，重新请求数据观察临期标记变化。修改后应恢复原值，避免影响后续演示。动态刷新有2026年11月8日的历史验收；11月9日主要验证真实家庭初始化与服务发现，没有重跑这一整套配置刷新场景。

代码入口：各服务application-cloud.yml、gateway的application.yml、fridge的config/FridgeSettings.java。操作细节见docs/开发运行手册.md的5.1.1节。

## 10 Feign让服务协作

### 为什么家庭服务要调用冰箱服务

家庭和成员归auth-family管理，冰箱和分区归fridge管理。用户只点击一次“创建家庭”，后端需要让这两个服务合作。如果只创建家庭，用户还要再手工创建冰箱；当前版本把默认冰箱一起初始化，减少一步操作。

Feign允许开发者写一个Java接口，声明服务名称、HTTP方法、路径、请求和返回类型。运行时它把接口调用转换为HTTP请求。它没有取消网络，也不会自动保证两个数据库一起成功。

当前接口片段可以简化理解为：

```java
@FeignClient(name = "fridge-service")
interface WorkspaceFridgeClient {
    // POST /api/v1/fridges
    // 传家庭编号、默认名称和认证信息
    // 接收创建后的冰箱编号
}
```

真实实现还支持FRIDGE_SERVICE_URL显式覆盖地址；日常留空才走Nacos发现。fridge回查家庭权限的FamilyAccessFeignClient也是实际使用场景，因此Feign不只出现在历史订单示例中。

### 请求中需要传递什么

除了业务参数，还传Authorization，让下游验证用户；传经过验证的用户信息；在内部调用中传Seata创建的TX_XID，使下游加入同一个全局事务。不能允许浏览器随意指定这张事务编号。

### 超时和业务错误需要分开

连接超时指建立连接等太久，读取超时指对方迟迟不返回。auth默认连接超时1000毫秒、读取超时5000毫秒；全局事务超时20000毫秒。权限不足、参数不合法与依赖不可用的含义不同，接口应保留可识别的错误结果。

fridge写入成功但响应丢失时，调用方会遇到失败；这也是后面需要Seata和幂等的原因。代码入口：auth/workspace/WorkspaceFridgeClient.java、WorkspaceFridgeGateway.java，以及fridge/family/FamilyAccessFeignClient.java。

## 11 Sentinel控制流量和故障扩散

### 限流是在入口控制进入速度

创建家庭需要写两个服务的数据库。短时间大量重复请求可能耗尽连接和线程，因此family-workspace-create资源设置默认每秒5次的限流规则。超过时返回HTTP429，并提示稍后重试。

QPS表示每秒请求数。这里的5是应用实例中该资源的规则，不是每个用户各有5次额度，也不是生产环境容量结论。日常只有一个auth实例；如果扩成多个实例，还需要重新设计和验证整体流量策略。

### 熔断是在下游变慢时暂时减少调用

假设fridge服务持续变慢，auth还不断等待它，就会积压大量请求。Sentinel观察family-fridge-initialize调用的慢请求比例，达到规则时临时停止调用，快速返回503，给下游恢复时间。

| 当前默认参数 | 作用 |
| --- | --- |
| 慢调用界线1500毫秒 | 超过该耗时计入慢调用 |
| 统计窗口10秒 | 在这段时间里统计完成调用 |
| 最少5次请求 | 样本不足时不会直接按比例熔断 |
| 慢调用比例0.5 | 达到相应比例条件时打开熔断器 |
| 熔断时间10秒 | 之后尝试探测恢复，成功后重新放行 |

参数可通过WORKSPACE_QPS、WORKSPACE_SLOW_CALL_MS和WORKSPACE_CIRCUIT_MIN_REQUESTS覆盖。实际触发以Sentinel规则和统计窗口为准，不能简单理解成“第六次一定失败”。

### 它与Feign超时有什么不同

Feign超时保护单次等待；Sentinel熔断根据一段时间的表现暂时阻止后续调用。限流控制进来的速度，熔断控制是否继续调用不健康依赖。权限不足等业务异常被排除在相应保护的异常统计之外。

Sentinel不会回滚数据库，也不会把失败变成功。11月9日的真实接口验收已经触发限流、慢调用熔断及恢复，并检查熔断期间没有继续请求下游。代码入口：WorkspaceProtection.java、WorkspaceService.java、WorkspaceFridgeGateway.java。

## 12 Seata协调跨服务事务

### 问题是两个服务可能只成功一半

创建家庭会先在auth_db写家庭和OWNER成员，再在fridge_db写冰箱、四区和六个容器。如果下游失败后只回滚auth自己的事务，就可能留下没有有效家庭的冰箱。用户期望的一次操作，需要有统一的成功或失败结果。

本项目在WorkspaceTransaction.create上使用@GlobalTransactional，Seata AT协调两个服务的数据库分支。auth负责发起全局事务，Seata Server负责协调，两个服务的代理数据源参与分支事务。

### 用一张办理单理解角色

| 名称 | 可以这样理解 | 当前对应 |
| --- | --- | --- |
| TM | 发起整件事情的人 | auth中的全局事务方法 |
| TC | 汇总进度并决定提交或回滚的协调者 | Seata Server |
| RM | 管理本地数据库分支的执行者 | auth和fridge的数据源代理 |
| XID | 贯穿整次操作的办理单编号 | 由后端创建，经内部Feign传播 |
| undo_log | 失败时恢复数据所需的回滚记录 | 两个业务库中的Seata表 |

### AT分两阶段工作

第一阶段，业务SQL和回滚日志在同一个本地事务中提交，并记录全局锁信息。第二阶段，全局成功时清理回滚日志；全局失败时根据日志补偿还原数据。这是分布式协调，不是把两个服务装进一个普通Java本地事务。

AT的第一阶段可能已经把数据提交到MySQL，所以普通读取不能天然认为“读到了就代表全局成功”。本项目额外使用workspace_pending、全局状态和新事务读取，防止未确定结果的家庭提前对外可用。

11月9日验收覆盖成功、下游拒绝、下游写完后响应丢失、写完后超时及同请求重试，并实际检查六类业务表变化和undo_log清理。Seata采用file单机配置，未验证协调者高可用。单库内食材和做饭操作仍使用本地事务，不需要每次都开启Seata。

## 13 重试与失败恢复

### 为什么界面超时后不能直接再建一次

网络超时只表示客户端没有及时拿到结果，不能证明后端一定没写入。假设服务已经提交，响应途中丢失，如果每次重试都当作新操作，就会出现重复家庭。

Flutter为一次创建意图生成requestId。后端以当前用户和requestId的组合建立唯一约束：同一用户、同一请求只对应一个创建结果。不同用户即使使用相同requestId，也不会读取对方的家庭。

| 场景 | 当前接口行为 |
| --- | --- |
| 首次创建并提交 | 201，返回家庭和冰箱编号 |
| 同一用户重放已提交请求 | 200，返回已有结果，不再创建 |
| 同请求编号换家庭名称 | 409，防止把不同意图混在一起 |
| 相同请求仍在处理 | 409，提示使用原请求稍后重试 |
| 请求过密 | 429，稍后再试 |
| 初始化依赖不可用或熔断 | 503，根据情况重试；事务协调回滚 |

这叫幂等，可以理解为“重复提交同一件事，不重复产生结果”。requestId不是登录令牌，也不是XID。requestId标识用户的一次意图；XID标识一次具体全局事务；Trace ID标识一次追踪。

### 当前实现的边界

客户端在当前进程内按用户和名称保留失败请求的requestId，成功后移除。它没有持久化跨重启的未完成请求编号。应用重启后应先读取服务端家庭列表，确认是否已存在，再发起新的创建。

服务端只在全局提交决定成立后确认成功。AT异步提交属于已经决定提交的状态，不能误报成失败。回滚后检查使用独立READ_COMMITTED读取，避免旧事务快照把已经回滚的家庭重新暴露出来。

用户可见的“撤销使用食材”属于业务操作，会追加新流水；Seata失败回滚属于技术恢复，二者不是同一按钮。代码入口：WorkspaceService、WorkspaceRepository、FamilyWorkspaceVisibility和Flutter的family_repository.dart。

## 14 SkyWalking定位一次操作

### 一次请求不是只经过一个函数

创建家庭从gateway进入auth，再调用fridge，fridge还会回查auth并访问MySQL。只看到一个“503”无法判断是网络、权限、数据库还是下游太慢。SkyWalking把后端的这些调用串成可查看的链路。

Java Agent随JVM启动，自动采集受支持框架的调用；OAP接收、分析和保存；UI显示服务和链路。它是观察工具，不负责限制流量，也不决定数据库提交。

### 三个名词如何读

Trace表示一次完整追踪。Span表示追踪里的一个步骤，例如一次HTTP调用或SQL。Trace ID是把这些步骤关联起来的编号。跨度很长的Span通常值得先排查，但耗时长本身不一定代表错误，需要结合结果和上下文。

| 观察到的现象 | 可以继续排查什么 |
| --- | --- |
| gateway很快，auth很慢 | auth内部逻辑或等待下游 |
| auth到fridge调用很慢 | 下游处理或网络等待 |
| SQL Span很慢 | 数据库连接、锁等待或SQL执行 |
| HTTP调用报错 | 查看状态、错误Span及对应服务日志 |

### 在本项目中如何使用

打开http://127.0.0.1:8088，选择auth-family服务、正确时间范围和创建家庭接口，再展开对应链路。成功链路应能看到服务协作和数据库访问。失败链路要结合回滚后的表数据判断恢复是否正确，不能只凭页面里有一条红色链路就宣称事务回滚通过。

11月9日已导出真实家庭创建成功和下游写后失败各一条追踪，保存在docs/reviews/evidence/2026-11-09-real-business/。详细Trace ID见trace-acceptance.json。

当前追踪从后端接收到HTTP请求开始，没有给Flutter配置客户端追踪SDK。界面按钮是触发源，但浏览器绘制过程不在这条后端Trace中。OAP使用H2单机存储，尚未验证长期大规模留存；服务、OAP和查询时间范围还需要保持一致时区。

代码入口：scripts/Start-Services.ps1中的-javaagent参数，以及scripts/query-family-workspace-traces.py。缺少Agent时脚本会警告，这时不能声称本次操作已被追踪。

## 15 MySQL和Flyway管理数据

### 数据库里的主要关系

| 数据库 | 主要记录 | 对应页面或功能 |
| --- | --- | --- |
| auth_db | app_user、refresh_session、family、family_member | 登录、家庭列表、成员权限 |
| auth_db | family_workspace_request | 创建家庭的请求编号、结果和全局事务状态关联 |
| fridge_db | fridge、fridge_zone、fridge_container | 当前冰箱、四个分区和储物位置 |
| fridge_db | food_item、food_operation | 食材数量、位置、到期日和操作时间线 |
| fridge_db | cook_record、cook_record_item | 一次做饭和每份食材的扣减明细 |
| recipe_db | recipe、recipe_ingredient | 菜谱信息、原料和步骤 |

表里的id是记录编号，family_id、fridge_id等字段表达归属。auth和fridge通过API协作，不应由前端任意跨库改记录。stock_db和order_db只属于历史商品交易示例。

### JdbcTemplate和HikariCP

JdbcTemplate把参数化SQL发送给数据库并转换查询结果。参数化查询把用户输入作为数据绑定，避免直接把输入拼进SQL。项目主要使用显式SQL访问，不使用MyBatis或JPA，介绍时不应把未使用的ORM框架加入技术栈。

HikariCP维护可复用的数据库连接池。建立连接有成本，连接池让多个请求依次复用连接，同时限制连接数量。连接池大小不是越大越好，还取决于数据库资源和并发方式。

### Flyway是数据库变化的版本记录

迁移文件以V1、V2等顺序编号。启动时Flyway检查已执行记录，执行尚未应用的迁移。新增字段或表时添加新迁移，不修改已经发布的旧迁移，以免其他电脑的校验和对不上。

本轮auth新增家庭初始化和可见性迁移，fridge新增Seata所需迁移。程序先让Flyway迁移原始数据源，再建立Seata代理，解决空库第一次启动时undo_log还不存在的问题。

代码入口：各业务服务src/main/resources/db/migration/，以及auth和fridge的config/TransactionalDataSourceConfig.java。H2用于自动化测试；真实MySQL行为仍需要实际环境验证。

## 16 并发修改与操作记录

### 两位成员同时使用鸡蛋会怎样

假设鸡蛋有5个，版本号是7。甲和乙都打开了详情。甲先使用2个，后端以版本7为条件更新成3个，并把版本加到8。乙仍用版本7提交时，更新条件不匹配，接口返回409，提醒刷新重试。

这个版本字段称为乐观锁。它不是把页面锁住，而是在提交时检查“你编辑的还是不是刚才那份数据”。数据库更新还检查数量，避免扣成负数。仅在界面禁用按钮无法处理两台设备同时操作。

### 操作流水为什么要单独保存

food_item表示现在的状态，food_operation记录怎么变成现在。新增、编辑、移动、使用、做饭扣减和丢弃都追加流水，包含操作者、时间、数量或位置变化。这样成员能理解库存变化，也能为允许撤销的操作提供依据。

| 操作 | 当前撤销能力 |
| --- | --- |
| 移动 | 可恢复到原分区和容器 |
| 使用和做饭扣减 | 可把扣掉的数量加回 |
| 丢弃 | 可恢复食材状态和数量 |
| 新增和整体编辑 | 旧字段快照不足，明确返回不支持撤销 |

撤销会写UNDO流水并标记原操作；恢复会写RESTORE流水并清除相应标记。并发撤销同一操作时，通过行锁和条件更新保证只有一次成功。恢复扣减时还要检查剩余数量，不能只做无条件减法。

### 本地事务管住同一个库里的多步写入

扣减食材和写操作流水必须一起成功。@Transactional或TransactionTemplate把相关SQL包进本地事务，失败时撤销这一组写入。做饭涉及多份食材，也在同一个fridge数据库的本地事务中完成。

丢弃采用状态变化而不是把历史彻底删除。时间线当前按条数限制读取，不是无限加载全部历史。代码入口：FoodRepository、FoodService、FoodOperationService和CookService。

## 17 菜谱匹配和做饭扣减

### 推荐依据来自现有数据

recipe服务提供六道种子菜谱及原料、可选标记和制作步骤。Flutter读取当前冰箱食材后，RecipeMatcher计算原料覆盖、缺少食材、临期匹配等信息，再排序展示。它是规则匹配，没有接入大语言模型生成菜谱，也不能保证营养或医疗建议。

例如冰箱里有番茄和鸡蛋，相关菜谱的已有原料覆盖会更高。缺少的原料在详情中列出，用户自己决定是否补充。这里没有商品价格、商家、支付和订单流程。

### 做饭不是自动猜测消耗

用户进入菜谱详情，选择“用现有食材做这道菜”，在确认弹层中勾选实际使用的食材并调整数量。后端校验每项是否属于当前冰箱、数量是否足够、版本是否仍一致，然后扣减并写做饭记录与COOK流水。

步骤可以这样复述：

1. 客户端提交菜谱信息、份数、requestId和食材扣减清单。
2. 后端验证当前家庭的编辑权限和全部食材。
3. 在一个本地事务内扣减多项食材，写主记录、明细和操作流水。
4. 任一项冲突则整组失败；成功后客户端重新加载库存。

请求编号以fridge_id和request_id组成唯一约束，同一次做饭重放返回已有记录，避免重复扣减。与创建家庭的幂等相比，这里的键按冰箱范围隔离；不能把两个接口的作用域混在一起。

### 当前记录能力到哪里

后端已经有做饭记录查询接口；用户端通过操作时间线能看到COOK变化，但独立做饭历史页尚未开发。用户可以撤销受支持的COOK操作，恢复数量时仍需遵守权限与当前数据条件。

代码入口：Flutter的recipe/domain/recipe.dart、recipe_controller.dart和cook_confirm_sheet.dart；后端的recipe-service及fridge-service/cook/。真正的补货入口是新增食材，不经过stock-service商品库存或order-service。

## 18 Docker和Nginx运行项目

### 容器把运行环境组织起来

Docker镜像可以理解为应用运行所需文件的模板，容器是由镜像启动的进程环境。Compose文件把中间件、端口、网络和数据卷写成配置。数据卷保存MySQL等状态，删除容器不等于一定删除数据；删除数据卷则可能造成数据丢失。

日常需要MySQL core、Redis、Nacos、Seata和SkyWalking，加四个业务应用和Web。core/full文件还包含历史或未接入组件，交付运行说明会按服务名称选择启动，避免把所有可选组件一次装进内存。

服务容器通过smart-fridge网络按名称通信。容器里的127.0.0.1指容器自身；手机上的127.0.0.1指手机自身，不能用它访问电脑后端。这是接手和Android联调中最常见的地址误区。

### Nginx让网页和API使用同一个来源

浏览器打开Web地址后，Nginx提供Flutter静态文件，把/api/请求代理给sf-gateway:8080。这样页面不需要写死另一台电脑的API地址，也减少跨域配置问题。HTTP来源由协议、主机和端口共同决定。

Web产物需要HTTP服务托管，不能双击index.html就当作完整运行。当前Web构建默认取页面来源作为API基址。Android构建则通过API_BASE_URL在构建时指定电脑地址。

### 构建工具各自生成什么

Maven把Java编译并打包成JAR；Flutter生成Web文件或APK；Vite生成管理端静态资源。Git记录源代码版本，ZIP负责交付文件，两者都不会自动安装Docker镜像和依赖。

运行脚本为每个业务JVM设置256MB最大堆并逐个等待健康，降低本机内存峰值。不要同时运行日常四服务和隔离验收四服务。Seata file与SkyWalking H2是单机开发配置，不能据此宣布生产可用。

接手人从docs/交付/交付与运行说明.md开始。开发工具只需按该文件准备，包内不包含本机数据库、Docker镜像和依赖缓存。

## 20 演示路线与常见问答

### 用一条用户路线讲清作品

先注册或登录真实账号，在家庭页创建一个家庭，回到首页确认已有默认冰箱。然后新增鸡蛋，查看食材、修改数量、移动分区，打开记录观察流水。进入菜谱选择一次做饭扣减，再返回库存查看变化。最后切换一个只读成员，验证能查看而不能修改。

讲中间件时回到创建家庭这个动作：Gateway接住请求，Nacos找实例，Feign让auth和fridge协作，Sentinel保护入口和慢依赖，Seata协调家庭及冰箱的提交，SkyWalking帮助看全过程。故障场景只在隔离验收环境演示，并结合数据库结果说明回滚。

### 可以直接使用的回答

**为什么不能把这些技术全写在手机里？** 用户端可以触发这些能力，服务发现、服务间事务和JVM Agent主要运行在服务器。手机负责界面和请求，服务器负责共享规则和数据库一致性。真正落地看是否服务于真实用户流程，而不是是否在手机上显示技术名称。

**Feign和Seata是不是都在调用服务？** Feign负责把请求送到另一个服务；Seata负责协调相关数据库分支成功或失败。能调用成功不代表遇到部分失败时仍然一致。

**补货为什么没有订单？** 当前产品只记录家庭食材入库，没有商家和购买关系。历史订单模块不参加这条路线，不能作为补货已实现的说明。

**做饭扣减为什么不用Seata？** 食材、做饭记录和流水都属于fridge_db，可以用本地事务完成；创建家庭跨auth和fridge两个服务，才使用全局事务。

**是不是已经做了AI推荐和智能硬件？** 当前是食材规则匹配和虚拟三维场景，没有大模型、摄像识别和实体冰箱控制。

**现在可以直接对外上线吗？** 当前适合课程交付与本地验收。正式上线仍需正式签名、HTTPS和密钥管理、部署安全、容量与恢复验证，以及未完成的真机验收。回答时应明确版本范围，不把构建成功说成全部验收完成。
