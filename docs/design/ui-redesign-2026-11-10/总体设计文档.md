# 小易冰箱 V2.0 · 黑白冷调厨房 UI 总体设计

日期：2026-11-10　｜　阶段：A 静白全景已确认并实施　｜　适用：Flutter Web / Android 用户端

本文件保留最初的总体设计及 A/B/C 比较。用户随后确认 A「静白全景」，正式 Flutter / Three.js 用户端已按 A 实施，并完成 18 道家常菜与独立新图。实施范围、实际截图、本机预览与验证边界见 [实施与预览](实施与预览.md)；下文的“现状”与选稿待确认项指 D0 提案时点，B/C 不作为当前产品基线。

后续用户反馈厨房过白，V2.0.1 已把场景调整为灰白黑并降低曝光/反射；最新 [实际截图](../../reviews/evidence/2026-11-10-kitchen-tone/home-desktop-closed.png) 与 [审查结果](../../reviews/2026-11-10-kitchen-gray-white.md) 替代最初的全浅色场景方向。

## 1. 设计目标

让用户感觉自己正在整理家里的冰箱。黑与白建立界面秩序，浅冷灰和低饱和灰蓝构成厨房环境，食材保留自然颜色。操作从“看厨房 → 找食材 → 使用或补充 → 安排一餐”自然展开。

核心原则：

1. 厨房真实可信：冰箱有实际体积、门缝、拉手和接地阴影；台面、柜体、窗光有一致的尺度与光照。
2. 界面安静：白底、近黑文字、黑色主按钮；去除大面积奶油色、橙色、暖木和装饰渐变。
3. 操作清楚：每个区域一个主要动作，按钮直接写“新增食材”“保存食材”“确认使用”，避免只有图标或含糊口号。
4. 状态可信：正在保存、保存失败、只读、冲突、无结果有明确反馈；不能用动效或颜色暗示数据已成功。
5. 手机可单手操作：主要动作和分区切换可触达，长表单能滚动，软键盘不遮住输入与错误。

| 当前界面 | 新设计处理 | 业务约束 |

## 3. 三套选稿方向

三套使用同一份示例库存和厨房参考图，方便比较布局本身。差异体现在空间分配、导航位置、信息密度和按钮形态，不依赖换一张背景图。

| 方案 | A · 静白全景（推荐） | B · 冷雾工作台 | C · 墨线橱窗 |
| --- | --- | --- | --- |
| 第一印象 | 明亮、安静，冰箱是主角 | 紧凑、有序，处理食材更快 | 黑白对比明确，建筑感更强 |
| 桌面结构 | 白色窄导航轨 + 大厨房场景 + 右侧今日清单 | 顶部导航 + 左场景/右工作台，摘要嵌入工作区 | 深色侧导航 + 横向厨房橱窗 + 宽清单 |
| 场景位置 | 中央最大视觉区 | 左侧约半屏，与食材清单平衡 | 顶部全宽横向场景，下方管理区域 |
| 按钮 | 12 px 圆角，黑实心主按钮 | 10 px 圆角，分段控件与紧凑操作栏 | 6 px 圆角，线性结构与近黑主按钮 |
| 环境色 | 冷白、淡石灰、少量雾蓝 | 灰蓝面积稍大，表面依旧白色 | 白色为主，深色仅用于导航与重点 |
| 适合偏好 | 真实厨房体验与日常易用性平衡 | 经常筛选、补录和调整食材 | 喜欢清晰框架、较高信息密度 |
| 需要确认 | 是否接受场景占用更多首屏 | 是否希望清单比场景更突出 | 是否接受整条深色导航 |

推荐 A：最接近“真实厨房 + 简约黑白”的要求，同时保留现有三维冰箱作为作品特色。B 更偏实际库存操作；C 提供更鲜明的黑白构图。

每套审查视图包含桌面首页、手机首页、清单与筛选、新增面板、食材详情、菜谱、家庭、登录及按钮状态。离线样稿可切换页面，并演示新增校验、只读、失败重试、危险确认和门控按钮状态。

## 4. 颜色与材质

### 4.1 共用语义色板

| Token | 色值 | 用途 |
| --- | --- | --- |
| `surface` | `#FFFFFF` | 表单、内容面板、主工作区 |
| `canvas` | `#F4F6F7` | 页面浅冷灰背景 |
| `ink` | `#171A1D` | 主文字、主按钮、已选按钮 |
| `ink-hover` | `#30363C` | 主按钮悬停 |
| `ink-pressed` | `#080B0E` | 主按钮按压 |
| `secondary-text` | `#59636D` | 次要文字 |
| `line` | `#DCE2E6` | 面板分隔与非交互边界 |
| `control-line` | `#85919B` | 输入框、次按钮等必需控件边界 |
| `cool-surface` | `#EAF0F3` | 浅冷场景底、次级选区背景 |
| `focus` | `#344F66` | 键盘焦点环，非品牌装饰色 |
| `danger` | `#963D45` | 破坏操作、过期与输入错误，配文字/图标 |
| `success` | `#345E50` | 成功反馈，配勾号与文字 |
| `warning` | `#735522` | 临期文字与提示图标，避免大面积黄色 |

界面视觉面积以白与浅冷灰为主，近黑用于文字、导航和主动作；灰蓝集中在厨房材质及少量次级表面。颜色比例是构图指导，不是运行时统计指标。食材与菜谱图片可以保留自然色，但不将其颜色扩展到整页。

### 4.2 厨房建模方向

- 柜门：下柜/高柜石墨灰，上柜中浅冷灰；台面深灰细颗粒石材，避免夸张大理石花纹。
- 墙面：中浅冷灰板材/砖面，接缝清楚；地面为中灰，形成不同于冰箱的明度层次。
- 冰箱：柔和灰白哑光金属外壳、近黑细门缝与拉手；降低反射和高光亮度。
- 光照：较低亮度的侧窗自然光与柔和环境光，保留接触阴影，防止大面积白色丢失细节。
- 道具：少量瓷碗、灰色布巾、水槽；保持台面整洁，避免植物/瓶罐堆积遮挡冰箱。
- 相机：默认正面轻透视，手机首屏完整显示冰箱；拖动后提供“复位视角”，不自动旋转。
- 生产实现仍使用已有 Three.js 几何、拾取与 Flutter 消息桥；本轮 `assets/kitchen-reference.png` 是生成的构图/材质参考，未实现开门动画或库存同步。

## 5. 信息架构与页面规则

主导航固定为「冰箱 / 菜谱 / 家庭」。桌面三种布局允许位置不同，手机统一三项底导航，冰箱/清单页在底栏并列放置独立「新增」动作，避免悬浮按钮遮挡门控；食材清单、操作记录通过冰箱页进入。切页保留已确认的筛选、滚动位置和三维实例，隐藏场景停止渲染与输入。

| 页面/状态 | 首要内容 | 主要动作与交互 |
| --- | --- | --- |
| 启动/登录/注册 | 小易冰箱、厨房参考、清晰表单 | 登录/注册一个主动作；密码可见性、错误定位、提交锁定 |
| 冰箱首页 | 当前家庭与冰箱、待处理食材、三维厨房、分区清单 | 新增食材；查看清单；开门/抽屉；复位视角 |
| 清单与筛选 | 名称搜索、分区、分类、标签、到期范围、排序 | 显示筛选结果数，清空筛选；筛选不改变场景的完整库存 |
| 新增/编辑 | 名称、分类、数量/单位、分区、购买/到期日期 | 保存；失败保留内容，关闭有修改草稿时确认 |
| 食材详情 | 数量、分区、分类、日期、到期文字 | 使用、移动、编辑；丢弃放在低优先级危险区 |
| 使用/移动 | 可见原数量/原分区与变更后结果 | 提交带版本；数量最多三位小数，边界沿用服务端 |
| 过期清理 | 只列确实已过期条目，今天到期不进入清理 | 二次确认；展示成功/跳过/失败，不承诺整批撤销 |
| 操作记录 | 时间、操作者、食材、增减、撤销状态 | 按接口能力显示单条撤销/恢复；ADD/UPDATE 不伪装为可撤销 |
| 菜谱列表/详情 | 真实菜名、已有原料/缺料、步骤、匹配口径 | 查看做法 → 选择扣减食材与份数 → 确认做饭 |
| 家庭与设置 | 当前家庭、角色、切换、成员、创建/加入 | OWNER 管成员；EDITOR 可写食材；VIEWER 只读 |
| 无家庭/无冰箱 | 简明说明与对应引导 | 创建家庭并初始化冰箱；已有家庭无冰箱时仅 OWNER 创建 |
| 失败/空结果/只读 | 原因、当前上下文、可执行的恢复动作 | 重试/清空筛选/返回；禁用旁写明原因 |

临期定义跟随后端配置，不在 UI 写死“三天”。原系统 `expiring` 可包含过期，首页呈现时明确区分“即将到期”和“已过期”，合计按同一快照计算，避免把过期食材纳入“今天推荐食用”。样稿日期固定为 2026-11-10，8 条库存中即将到期 3 条、已过期 1 条，仅为设计演示。

## 6. 按钮、表单与反馈规范

### 6.1 按钮等级

| 等级 | 样式 | 例子 | 规则 |
| --- | --- | --- | --- |
| 主要 | 近黑底、白字、可带线性图标 | 新增食材、保存食材、确认使用 | 每个局部任务一个主要按钮，不整页重复黑块 |
| 次要 | 白底、可辨识灰边、近黑字 | 食材清单、查看记录、取消 | 同主按钮等高，依次排布 |
| 文字 | 无底、近黑文字 + 明确语义 | 查看全部、重置筛选 | 小型辅助动作，不承载关键提交 |
| 危险 | 深红文字/边框，确认层可深红实心 | 丢弃、清理过期、移除成员 | 带对象与后果说明，默认焦点不落在确认危险按钮 |
| 切换 | 未选白底，已选近黑底白字 | 分区、三维门控 | 多门可同时开启，各自独立高亮；概览不冒充开启 |
| 图标 | 至少 44 × 44 px 命中区 | 关闭、刷新、复位 | 有可访问名称和桌面提示，不靠悬停才能操作 |

桌面按钮常规高度 44 px，手机主要动作 48 px；输入框 48 px。按钮间距至少 8 px，危险操作与普通操作间距至少 16 px。标签不因加载消失：转为“正在保存…”并显示转圈，占位宽度不跳动。

### 6.2 必须展示的状态

| 状态 | 视觉 | 行为 |
| --- | --- | --- |
| 默认 | 黑/白等级明确 | 可点击、可键盘触达 |
| 悬停 | 主按钮略提亮，次按钮浅灰底 | 120 ms 颜色过渡，无漂浮大阴影 |
| 按下 | 主按钮更深，最多 1 px 下移 | 命中范围不缩小，禁用时无按压反馈 |
| 焦点 | 2 px 深灰蓝外环 + 2 px 间隙 | 不去掉浏览器/Flutter 焦点可见性 |
| 提交中 | 转圈 + 正在保存，禁用相关写入口 | 防重复提交；关闭/切家庭遵循任务中规则 |
| 成功 | 勾号 + 明确结果 | 服务端确认后更新；“新增”不提供伪撤销，丢弃按实际时间线撤销 |
| 失败 | 表单内错误 + 重试入口 | 草稿与滚动保留，重新提交同一幂等请求按既有契约 |
| 禁用 | 浅灰底、灰字；旁附原因 | 不能触发写请求；只读说明始终可见 |

### 6.3 关键操作流程

- 新增：打开空表单 → 名称/数量/日期校验 → 点击保存 → 提交锁定 → 成功关闭并刷新；失败留在面板。关闭修改过的草稿时提供“继续填写 / 放弃修改”。
- 使用：显示当前数量与单位 → 步进或手填 → 显示使用后剩余 → 确认。不能负数、超量、超过三位小数；冲突提示“库存已更新，请刷新后重试”，不回写旧库存。
- 分区：切换分区后同步清单；门/抽屉按钮独立控制模型开合。显示储存参考温度，不能被理解为可控制设备温度。
- 丢弃/清理：先列对象和数量，再确认；成功提示条提供“查看记录”，只有真实可撤销记录才展示撤销。
- 做饭：详情进入扣减确认，用户逐项选择数量；使用既有 `requestId` 幂等机制；失败不会把已提交任务当作未提交重复扣减。
- 家庭切换：先处理未保存草稿，再切换；立即撤下旧家庭库存并显示加载。成功/失败都检查请求家庭和当前家庭一致，禁止旧请求覆盖。

## 7. 布局、字体与动效

桌面基准 1440 × 960，手机 390 × 844；同时检查 320、768、1024、1440、1920 宽度。最大正文宽度约 1600 px，大屏用留白承接，不无限拉宽文字。小于 1100 px 收起复杂并排区域，小于 760 px 变为纵向布局与底导航。

- 间距以 4/8 px 为基本单位，常用 16/24/32 px。正文 14–16 px，页标题 28–36 px，辅助文字至少 12 px；长中文按钮允许合理换行，数值与单位不拆开。
- 字体沿用本地 Xiaoyi UI 并使用系统中文回退，包含常规和半粗字重，不依赖外网字体。
- 线性图标统一 1.5–1.8 px，20–24 px；避免混用彩色表情和不同粗细图标。
- 桌面表单为约 440–480 px 侧抽屉；手机为可滚动全宽面板，底部保存区考虑安全区与软键盘。弹层打开后暂停场景输入，关闭恢复焦点到触发按钮。
- 按钮 120 ms；页面/面板 180–220 ms；门/抽屉沿用自然开合约 320–450 ms。支持系统减少动态效果，取消位移与自动动效。
- 正文对比度目标至少 4.5:1，必要控件边界与焦点至少 3:1；错误、临期、已选均配文字/图标，不只靠颜色。
- 键盘顺序与阅读顺序一致；弹层锁定焦点，Esc 进入关闭/草稿确认流程，焦点回到触发入口；提交错误定位到第一处字段。

## 8. 审查包如何使用

打开 `index.html` 进入审查入口，也可直接打开 `prototype.html?scheme=a`（b/c 同理）。全部本地资源，无后端请求，输入内容仅保存在当前样稿内存中，刷新即重置。

建议顺序：

1. 先看 `review-a.png / review-b.png / review-c.png`，比较桌面/手机和页面细节。
2. 进入任意方案，切换「冰箱 / 菜谱 / 家庭」，再看清单、详情、记录和登录页。
3. 点击新增：空提交看字段错误；正常提交看加载与反馈；“审查控制”可切换只读或模拟一次失败，查看重试与草稿保留。
4. 在清单尝试名称、分区与到期筛选；在详情尝试丢弃确认；在首页尝试门控按钮独立高亮。

样稿中的门控仅示意控制状态，厨房参考图不会开门；没有实际接入业务、WebGL、鉴权、持久化或网络失败。只读切换属于审查工具，不是正式用户设置。截图、自动检查和产品端到端验收分别记录。

用户确认项：A/B/C 整体布局；黑色导航面积；场景与清单比例；按钮圆角与密度；手机新增入口及面板形式。允许选择“A 的布局 + B 的清单密度”等组合，再收敛一套实施稿。

## 9. 确认后的实施与阶段审查

本轮停在选稿，不自动进入正式 UI 实现。这是用户“先给总体设计文档和三套审查视图让我确认”的明确顺序要求。原有常规阶段自动推进约定继续适用于确认后的开发。
